過程中釐清的兩件事，記下來免得日後重踩：

   要比較 Compose 的組合成本，用 Java Heap，不要用 janky frames。

### 四位數集數被截成刪節號（2026-09-15）

| 項目 | commit | 驗證 |
|---|---|---|
| 修正集數按鈕的截斷規則 | `2b7447a` | 抽出 `episodeButtonLabel` 並補 5 個單元測試（含突變測試） |

實機上航海王的集數區整片顯示成「第1141…」「第1142…」，完全看不出是第幾集。
根因不是按鈕太窄，是這條規則：

```kotlin
val label = if (rawLabel.length > 5) "${rawLabel.take(5)}…" else rawLabel
```

「第1141集」剛好 6 個字，截完變成 7 個字的「第1141…」——**比原文還長**，純粹是反效果。
原註解寫門檻 5 是要配合「第01集」「第123集」，沒考慮到四位數。

截斷的本意是處理「聖光篇 第1集」這種具名標題，純集數標題（`第?\d+集?`）不該進去。
修好後手機 4 欄與 TV 10 欄都能完整顯示「第1141集」。

## 二、確定要修（依執行順序）

### 第一批：更新流程（使用者按得到的 bug，且有時間壓力）

> **為什麼排第一**：`e7033d0`（9/12 22:16）加 callTimeout 後，下載路徑出現迴歸。≤v3.1.11 的使用者不受影響，但 **v3.1.12+ 升級到下一版時就會撞到**。而取消功能是整個壞的。

#### 1. 取消路徑的三個 bug（必須一起修）

這三個是同一個症狀「按取消沒反應、過一下跳下載失敗」的三個成因，**分開修都不夠**：

| 位置 | 問題 | 修法 |
|---|---|---|
| `UpdateController.kt:160-171` | 下載迴圈是阻塞 okio read，無 suspension point，`Job.cancel()` 完全無效，執行緒繼續全速下載 | 迴圈內每輪加 `coroutineContext.ensureActive()`，`catch`/`finally` 裡 `target.delete()` |
| `:85-87` | `catch (e: Exception)` 把 `CancellationException` 一起接住 → 設成 `Error("下載失敗: StandaloneCoroutine was cancelled")` | `catch (e: CancellationException) { throw e }` 放在一般 catch 之前 |
| `:76-84` | 進度回呼的 else 分支把狀態**復活成 Downloading**。節流是 200ms → 「剩餘時間/200ms」次，實務上數十次 | 回呼裡先確認自己仍是當前 job；或 else 分支改成 `else prev`（不動） |

**使用者現在看到的**：按「取消下載」→ 對話框閃一下就回到「下載中」→ 再按還是一樣 → 直到孤兒執行緒死掉才跳出「下載失敗」。**等於取消功能整個失效。**

**驗證方式**：觸發一次下載，按取消，確認 (a) 進度條停止 (b) 不會跳出「下載失敗」(c) 網路流量停止。

> 檔案系統層面**不會壞資料**：`:147` 的 `delete()` 在 Linux 上只是 unlink，舊 FD 仍指向原 inode，新下載以 `O_CREAT` 建出另一個 inode，兩條執行緒寫不同 inode 不會交錯污染。實際代價是孤兒 inode 佔磁碟直到 FD 關閉、以及兩份下載並行吃頻寬。

#### 2. 安裝中斷後不要回不去

| 位置 | 問題 | 修法 |
|---|---|---|
| `:116` | `launchInstaller()` 後立刻把 state 設成 `Idle`。使用者在系統安裝畫面按返回，那份下好的 APK **再也接不回來**，只能整包重下 | 保留 `ReadyToInstall`，改由使用者關閉或下次 check 才清 |
| `:102` | 狀態不是 ReadyToInstall 時 `?: return true`（回報成功）→ `UpdateOverlay.kt:80` 的「重試安裝」會把對話框關掉卻什麼也沒裝 | 改成 `return false` |
| `:54` + `SettingsScreen.kt:92` | 只擋 `Checking`/`Downloading`，沒擋 `ReadyToInstall` → 在已下載完成時按「檢查更新」，state 被設成 Checking，**APK 參照遺失** | `enabled` 條件加上排除 `ReadyToInstall` |

> `81e8b35` 修掉的是「權限對話框那條死巷」，這幾條是**不同的死巷**，還在。

#### 3. 下載完成要驗證落檔大小

`:154` 的 `total` 只當進度分母，結束時沒有比對 `target.length() == total`，也沒用 GitHub asset 的 `info.sizeBytes`（**明明已經有**）。截斷檔多數情況會由 OkHttp 丟 `ProtocolException`，但不保證；漏網的話使用者會看到系統的「解析套件時發生問題」。

**修法**：`:176` 前加 `check(target.length() == info.sizeBytes)`，不符就刪檔報錯。

#### 4. 下載改用專用 client

```kotlin
private val downloadClient by lazy {
    okHttpClient.newBuilder()
        .callTimeout(0, TimeUnit.MILLISECONDS)   // 下載不設絕對上限
        .readTimeout(10, TimeUnit.SECONDS)       // 縮短：這才是取消延遲的真正來源
        .cache(null)                             // 不要讓 APK 佔 20MB 共用快取
        .apply {
            interceptors().removeAll {           // 不可用 clear()，會誤刪 UA interceptor
                it is CloudflareInterceptor || it is SearchRateLimitInterceptor
            }
        }
        .build()
}
```

**為什麼這樣改是安全的**：`e7033d0` 加 callTimeout 的意圖是約束「十二處抓取用的 `execute()`」，commit 明說「取 20 秒是絕對不該超過的上限」。給下載開一個例外**不動全域設定**，完全符合原意圖。`newBuilder()` 共用連線池，不新增資源。

> `interceptors()` 回傳的是活的 `MutableList`（已用 `javap` 驗證 okhttp-4.12.0），可以 `removeAll`。但**不可 `clear()`**：`NetworkModule.kt:71-87` 那個匿名 UA/Accept interceptor 會一起被清掉，退回 `okhttp/4.12.0` UA。

#### 5. 「立即更新」的重入

state 要等**第一次進度回呼**才變 Downloading，在 connect（8s）+ 首個 200ms 之前狀態仍是 `Available`，AvailableDialog 還在畫面上。**TV 遙控器重按確認鍵極易觸發**，會開出多條下載（而舊的 cancel 無效，見 #1）。

**修法**：`startDownload` 進入時立刻 `_state.value = Downloading(info, 0, info.sizeBytes)`。

#### 6. 安裝成功後清掉 APK

清理只在 `:147`（下次下載開頭）。安裝成功後那份 APK 會一直留在 cacheDir。應在 `launchInstaller` 成功或 dismiss 時清。

### 第二批：播放器（TV 使用者每次看片都會碰到）

#### 7. TV 遙控器失效 — 但要先做一個架構決定

**已實證**：快轉 30 次，播放位置只前進 20 秒（＝自然播放時間）。OK 鍵不暫停、不叫控制列，上下鍵無反應。

**根因**：`setOnKeyListener` 只在該 View **自己持有 View 焦點**時才會被呼叫。Compose 端全檔 0 個 `requestFocus`，正常播放時是 AndroidComposeView 吃著 View 焦點 → `PlayerScreen.kt:211-239` 的 **LEFT/RIGHT 與 BACK 分支都是死碼**。BACK 仍有效是走 NavHost 的 OnBackPressedDispatcher，進度有存是 `onDispose` 代勞——**這就是為什麼長期沒人抱怨**。

**⚠️ 原案「給 PlayerView requestFocus」是錯的**：PlayerView 建構時設了 `FOCUS_AFTER_DESCENDANTS`（已反編譯 media3-ui 1.9.0 確認），控制列一顯示焦點就會被吸進 `PlayerControlView` 的按鈕，第一次快轉後 LEFT/RIGHT 就變成按鈕導航。而且 `onPlaybackFailed:351-354` 只設 `error` 沒清 `streamUrl`，PlayerView 會留在錯誤遮罩底下持有焦點 → **「切換線路重試」按鈕真的按不到**。

**⚠️ 第二輪發現替代案也有坑**：把 Compose `Box` 疊在 `AndroidView` 上層仍是**兄弟節點不是祖先**，`Modifier.onKeyEvent` 只在焦點落在自己子樹內才觸發，控制列一出現照樣失焦——**等於換個寫法重蹈覆轍**。

**所以必須先做這個決定：**

| 方案 | 做法 | 代價 |
|---|---|---|
| **A. Compose 自畫控制列** | `useController = false` + PlayerView 設 `FOCUS_BLOCK_DESCENDANTS`，控制列與所有按鍵都由 Compose 處理 | 要自己畫控制列 UI；但焦點歸屬完全可控，也順便解決換集/換線入口的問題 |
| **B. 保留 media3 控制列** | 維持 `useController = true`，改成把按鍵處理掛在 PlayerView 的 `dispatchKeyEvent` 或自訂 `PlayerControlView` | 改動小，但焦點在 Compose 與 View 之間的來回仍需小心處理 |

**這個決定會連動 #8**（見下）。無論選哪個，都要一併：

## 三之三、功能驗證抓到的缺陷（2026-09-15）

稽核清單之外，逐畫面驗證功能時抓到的。

| 項目 | commit | 驗證 |
|---|---|---|
| 片名裡的 & 顯示成 amp | `(片名解碼)` | 13 處取標題的屬性；7 個單元測試，對兩條路徑各做突變驗證 |

**診斷過程值得記下來，因為第一次是錯的。**

實機在電視劇分類看到片名顯示成「S&amp;X」。第一版診斷是「Jsoup 的 `attr()` 不解 HTML entity，
`text()` 才會」，照這個寫了修正與 4 個測試，全綠。做突變測試把修正改回原樣——**測試還是全綠**，
代表測試根本沒測到修正。

`curl` 抓站台原始 HTML 才看到真相：

```
aria-label="S&amp;amp;X"     ← 站台把片名編碼了兩次
```

Jsoup 的 `attr()` 本來就會解一次（實測驗證過），解完是 `S&amp;X`，畫面就照這樣顯示。
根因是站台雙重編碼，不是 Jsoup 沒解。原本的測資用單重編碼，Jsoup 自己就解掉了，
所以測試有沒有修正都會過——一組假綠的測試。

改用雙重編碼當測資後，兩個突變（把 aria-label、img alt 各自改回 `attr()`）才精準轉紅。

修正本身是對的（多解一次），但註解、commit 訊息、測資全部要照真相重寫。

**實機驗證**：同一格片名從「S&amp;X」變成「S&X」。
順帶一提 uiautomator dump 的 `text` 屬性是 XML 編碼過的，要用 XML parser 解碼後再比對，
直接 grep 會判斷錯。
