## 兩個決定性實證

### 實證 1：TV 快轉完全沒有生效

爭議點：靜態分析說 `PlayerScreen.kt:211-239` 的 `setOnKeyListener` 是死碼，Codex 認為「不能靜態推論，要實機驗」。

做法：TV 模擬器上播放，用 `run-as` 讀 Room 的 `positionMs`，按 30 次 `DPAD_RIGHT`（若生效應前進 300 秒），再讀一次。

```
快轉前：pos = 26,412 ms
按 30 次 DPAD_RIGHT
快轉後：pos = 46,465 ms
差值   = 20,053 ms ≈ 20 秒 = 正好等於自然播放經過的時間
```

**結論：快轉一次都沒有生效。** 若生效，差值應該是 320 秒以上。

### 實證 2：返回詳情頁後，已看標記完全消失

做法：播放「中頭獎還是要上班」第 2 集（DB 已記錄 `episodeNum=2`），按 BACK 返回詳情頁。

結果：集數區的「第01集」「第02集」**兩個都是灰底，沒有任何已看高亮**。

原因：`DetailViewModel.loadWatchProgress()` 是 `init` 裡一次性的 `getProgress()`，而 Detail 的 NavBackStackEntry 在播放器疊上來時只是 STOPPED 不是 DESTROYED，返回時 `init` 不再跑。

## 一、不要修（審查後撤銷）

這五項是初版報告的**誤判或過度診斷**。照原案修會讓現況變差。

### ❌ C-4「死線路記錄形同虛設」— 描述錯誤

初版寫「從頭到尾沒有被讀過」。實際上：

```kotlin
// PlayerViewModel.kt:348-349
failedPlaybackSourceIds += _uiState.value.sourceId
val next = detail.episodes.firstOrNull { it.sourceId !in failedPlaybackSourceIds }
```

三個獨立來源（第一輪紅隊、Codex、我本人覆核）一致確認**它有在運作**。真正的缺口只有「`switchSource:301` 的 candidates 沒過濾」這一小塊。

**而且原案修法會製造死局**：網路短暫斷線 → 全部線路被標記失敗 → candidates 空 → 該集合只在 `loadPlayer:86` 與 `switchEpisode:285` 清除，`switchSource` 不清 → 使用者按「切換線路重試」永遠救不回來。比現況更糟。

> 若真要動：改成**降權排序**而非排除，改在 `orderedSourcesFrom(:246-254)`（三個入口的唯一收斂點），用穩定排序 `sortedBy { it.sourceId in failed }` 做二分區，區內 tier 順序原樣保留，不會跟「順暢雲優先」打架。但這屬於優化，不是修 bug。

### ❌ C-8「空結果被當成功寫入快取」— 是刻意設計

`757adbc`（2026-09-11）的 commit 訊息寫得很清楚：

> 改為區分「來源有回應但沒有符合的片」與「來源整個失敗」，只有前者才進快取。

程式碼用 `null` 代表整個失敗、非 null 代表有回應。原案建議的「`answered` 再加條件『至少一個來源有 items』」會**直接撤銷這個決定**：真正搜不到的關鍵字（冷門片名、第 2 頁以後沒東西、成人來源被關）每次重試都會重打 8 個站 × 5 秒，等於對站台自我 DDoS。

**真正的洞在別處**（見「三、確定要修」的 #14）：`anySourceAnswered` 算出來卻被丟掉，UI 無法分辨「全站掛掉」與「真的沒有」，兩者都顯示「找不到」。

### ❌ C-11「Hero 吞掉左右鍵」— 是刻意的 affordance

```kotlin
// HomeScreen.kt:391
Text(if (btnFocused) "◀  觀看詳情  ▶" else "▶  觀看詳情", ...)
```

聚焦時標籤明講左右可切換 banner。改成「保留一側可離開」會讓標籤說謊。而且 `items` 來自 `rows.firstOrNull()?.items?.take(6)`，單張 banner 是假想邊界。

> 若真要防禦：只加 `if (items.size <= 1) return@onPreviewKeyEvent false`，不要碰「保留一側」。

### ❌ C-13「加 UNIQUE 索引」— 一半是假陽性，且修法有實害

- **watch_history 是假陽性**：`WatchHistoryRepositoryImpl.kt:38` 先 `getByVod` 取回 `existing?.id` 再帶進 entity，`REPLACE` 靠 **PK 衝突**生效，去重一直在運作。
- **favorites 理論上會重複**，但實機驗證：收藏頁只有 2 筆、沒有重複；連點兩次「收藏」的結果是 toggle 兩次回到原狀，沒有產生重複列。
- **原案修法有三個實害**：
  1. 去重 migration 若用 `keep MIN(id)`，watch_history 會保留最舊那筆 → **播放進度直接倒退**
  2. `REPLACE` 一旦真的生效，`FavoriteRepositoryImpl.kt:39-48` 沒帶 `addedAt`/`missCount` → 重新收藏會把 `addedAt` 重設成 now（`Daos.kt:9` 是 `ORDER BY addedAt DESC`，**收藏列表順序會跳動**）、`missCount` 歸零
  3. `Daos.kt:32-41`/`:93-102` 的 `relink` 是 UPDATE，撞上新約束會拋 `SQLiteConstraintException`，而整段包在 `runCatching` 裡 → **失效收藏的自動修復會靜默失效**

> 這一項唯一該做的是：若日後採用「三重存檔」類修法（見 #7 的警告），必須先補 DAO 層的 `@Transaction upsertByVod`，否則會引爆重複列。

### ❌ overscan「詳情頁捲動後貼齊畫面頂緣」— 我的實測證據對不上修法

`DetailScreen` 從頭到尾沒有用過 `screenVerticalPadding`（`Dimensions.kt:30`）。我實測到的現象是 LazyColumn 捲動的本質——任何捲動內容都會到達 y=0，**這不是 bug**。

> `TvDimensions` 的 `screenVerticalPadding` 20→27dp 可以改（1080p 的 5% 安全區是 27dp，且 `Dimensions.kt` 有 Tv/Tablet/Phone 三份，不影響手機），但它只作用在 6 個頁面的 TopBar，別宣稱它修好了詳情頁。

## 二、確定要修（依執行順序）

### 第一批：更新流程（使用者按得到的 bug，且有時間壓力）

> **為什麼排第一**：`e7033d0`（9/12 22:16）加 callTimeout 後，下載路徑出現迴歸。≤v3.1.11 的使用者不受影響，但 **v3.1.12+ 升級到下一版時就會撞到**。而取消功能是整個壞的。

#### 1. 取消路徑的三個 bug（必須一起修）

這三個是同一個症狀「按取消沒反應、過一下跳下載失敗」的三個成因，**分開修都不夠**：

| 位置 | 問題 | 修法 |
|---|---|---|
| `UpdateController.kt:160-171` | 下載迴圈是阻塞 okio read，無 suspension point，`Job.cancel()` 完全無效，執行緒繼續全速下載 | 迴圈內每輪加 `coroutineContext.ensureActive()`，`catch`/`finally` 裡 `target.delete()` |
| `:85-87` | `catch (e: Exception)` 把 `CancellationException` 一起接住 → 設成 `Error("下載失敗: StandaloneCoroutine was cancelled")` | `catch (e: CancellationException) { throw e }` 放在一般 catch 之前 |
| `:76-84` | 進度回呼的 else 分支把狀態**復活成 Downloading**。節流是 200ms → 「剩餘時間/200ms」次，實務上數十次 | 回呼裡先確認自己仍是當前 job；或 else 分支改成 `else prev`（不動） |

**使用者現在看到的**：按「取消下載」→ 對話框閃一下就回到「下載中」→ 再按還是一樣 → 直到孤兒執行緒死掉才跳出「下載失敗」。**等於取消功能整個失效。**

**驗證方式**：觸發一次下載，按取消，確認 (a) 進度條停止 (b) 不會跳出「下載失敗」(c) 網路流量停止。

> 檔案系統層面**不會壞資料**：`:147` 的 `delete()` 在 Linux 上只是 unlink，舊 FD 仍指向原 inode，新下載以 `O_CREAT` 建出另一個 inode，兩條執行緒寫不同 inode 不會交錯污染。實際代價是孤兒 inode 佔磁碟直到 FD 關閉、以及兩份下載並行吃頻寬。

#### 2. 安裝中斷後不要回不去

| 位置 | 問題 | 修法 |
|---|---|---|
| `:116` | `launchInstaller()` 後立刻把 state 設成 `Idle`。使用者在系統安裝畫面按返回，那份下好的 APK **再也接不回來**，只能整包重下 | 保留 `ReadyToInstall`，改由使用者關閉或下次 check 才清 |
| `:102` | 狀態不是 ReadyToInstall 時 `?: return true`（回報成功）→ `UpdateOverlay.kt:80` 的「重試安裝」會把對話框關掉卻什麼也沒裝 | 改成 `return false` |
| `:54` + `SettingsScreen.kt:92` | 只擋 `Checking`/`Downloading`，沒擋 `ReadyToInstall` → 在已下載完成時按「檢查更新」，state 被設成 Checking，**APK 參照遺失** | `enabled` 條件加上排除 `ReadyToInstall` |

> `81e8b35` 修掉的是「權限對話框那條死巷」，這幾條是**不同的死巷**，還在。

#### 3. 下載完成要驗證落檔大小

`:154` 的 `total` 只當進度分母，結束時沒有比對 `target.length() == total`，也沒用 GitHub asset 的 `info.sizeBytes`（**明明已經有**）。截斷檔多數情況會由 OkHttp 丟 `ProtocolException`，但不保證；漏網的話使用者會看到系統的「解析套件時發生問題」。

**修法**：`:176` 前加 `check(target.length() == info.sizeBytes)`，不符就刪檔報錯。

#### 4. 下載改用專用 client

```kotlin
private val downloadClient by lazy {
    okHttpClient.newBuilder()
        .callTimeout(0, TimeUnit.MILLISECONDS)   // 下載不設絕對上限
        .readTimeout(10, TimeUnit.SECONDS)       // 縮短：這才是取消延遲的真正來源
        .cache(null)                             // 不要讓 APK 佔 20MB 共用快取
        .apply {
            interceptors().removeAll {           // 不可用 clear()，會誤刪 UA interceptor
                it is CloudflareInterceptor || it is SearchRateLimitInterceptor
            }
        }
        .build()
}
```

**為什麼這樣改是安全的**：`e7033d0` 加 callTimeout 的意圖是約束「十二處抓取用的 `execute()`」，commit 明說「取 20 秒是絕對不該超過的上限」。給下載開一個例外**不動全域設定**，完全符合原意圖。`newBuilder()` 共用連線池，不新增資源。

> `interceptors()` 回傳的是活的 `MutableList`（已用 `javap` 驗證 okhttp-4.12.0），可以 `removeAll`。但**不可 `clear()`**：`NetworkModule.kt:71-87` 那個匿名 UA/Accept interceptor 會一起被清掉，退回 `okhttp/4.12.0` UA。

#### 5. 「立即更新」的重入

state 要等**第一次進度回呼**才變 Downloading，在 connect（8s）+ 首個 200ms 之前狀態仍是 `Available`，AvailableDialog 還在畫面上。**TV 遙控器重按確認鍵極易觸發**，會開出多條下載（而舊的 cancel 無效，見 #1）。

**修法**：`startDownload` 進入時立刻 `_state.value = Downloading(info, 0, info.sizeBytes)`。

#### 6. 安裝成功後清掉 APK

清理只在 `:147`（下次下載開頭）。安裝成功後那份 APK 會一直留在 cacheDir。應在 `launchInstaller` 成功或 dismiss 時清。

### 第二批：播放器（TV 使用者每次看片都會碰到）

#### 7. TV 遙控器失效 — 但要先做一個架構決定

**已實證**：快轉 30 次，播放位置只前進 20 秒（＝自然播放時間）。OK 鍵不暫停、不叫控制列，上下鍵無反應。

**根因**：`setOnKeyListener` 只在該 View **自己持有 View 焦點**時才會被呼叫。Compose 端全檔 0 個 `requestFocus`，正常播放時是 AndroidComposeView 吃著 View 焦點 → `PlayerScreen.kt:211-239` 的 **LEFT/RIGHT 與 BACK 分支都是死碼**。BACK 仍有效是走 NavHost 的 OnBackPressedDispatcher，進度有存是 `onDispose` 代勞——**這就是為什麼長期沒人抱怨**。

**⚠️ 原案「給 PlayerView requestFocus」是錯的**：PlayerView 建構時設了 `FOCUS_AFTER_DESCENDANTS`（已反編譯 media3-ui 1.9.0 確認），控制列一顯示焦點就會被吸進 `PlayerControlView` 的按鈕，第一次快轉後 LEFT/RIGHT 就變成按鈕導航。而且 `onPlaybackFailed:351-354` 只設 `error` 沒清 `streamUrl`，PlayerView 會留在錯誤遮罩底下持有焦點 → **「切換線路重試」按鈕真的按不到**。

**⚠️ 第二輪發現替代案也有坑**：把 Compose `Box` 疊在 `AndroidView` 上層仍是**兄弟節點不是祖先**，`Modifier.onKeyEvent` 只在焦點落在自己子樹內才觸發，控制列一出現照樣失焦——**等於換個寫法重蹈覆轍**。

**所以必須先做這個決定：**

| 方案 | 做法 | 代價 |
|---|---|---|
| **A. Compose 自畫控制列** | `useController = false` + PlayerView 設 `FOCUS_BLOCK_DESCENDANTS`，控制列與所有按鍵都由 Compose 處理 | 要自己畫控制列 UI；但焦點歸屬完全可控，也順便解決換集/換線入口的問題 |
| **B. 保留 media3 控制列** | 維持 `useController = true`，改成把按鍵處理掛在 PlayerView 的 `dispatchKeyEvent` 或自訂 `PlayerControlView` | 改動小，但焦點在 Compose 與 View 之間的來回仍需小心處理 |

**這個決定會連動 #8**（見下）。無論選哪個，都要一併：
- `PlayerScreen.kt:184` 的顯示條件加上 `uiState.error == null`（讓錯誤時 PlayerView 退出焦點鏈）
- **不要**把 `streamUrl` 設成 null（會拆掉 AndroidView、留下已 detach 的髒參照 `playerView:98`）

#### 8. 生命週期（與 #7 綁定）

**已實測**：按 HOME 後 12 秒仍持有 audio focus（`gain: GAIN, loss: none`），背景 10 秒消耗 **557 jiffies = 5.57 秒 CPU**（前景對照 793），影片還在全速解碼。

**修法**：加 `LifecycleEventObserver`，**只做 `ON_STOP → saveProgress + pause`，不做自動恢復**。

**⚠️ 與 #7 的硬衝突**：不自動恢復的前提是「media3 的 `controllerAutoShow` 會在暫停時自動顯示控制列並把焦點送到播放鍵」。**若 #7 選了方案 A（關掉 useController），這條恢復路徑就不存在了**，必須由 Compose 自己負責「暫停時顯示控制列 + 焦點給播放鍵」。

**⚠️ 三重存檔警告**：若同時加 `BackHandler`，退出時 `saveProgress` 會被呼叫三次（BackHandler + ON_STOP + `onDispose`）。NavHost 下 ON_STOP 與 BackHandler 落在**同一個 main thread turn**，兩個協程同時掛在 `getByVod` → 首次觀看時雙雙讀到 null → **插兩列**。首頁「繼續觀看」與歷史頁都沒有 distinctBy，會出現兩張一模一樣的卡。

> 目前**沒有**這個問題（BACK 與 `onDispose` 被 700ms 退場動畫隔開，且首列通常已由 10 秒自動存檔建立）。這是「採用修法後才會引爆的地雷」。要加 BackHandler 就必須先補 DAO 層 `@Transaction upsertByVod`。

#### 9. 返回詳情頁後已看標記消失（實證確認）

**修法**：DAO 加 `fun observeByVod(vodId, sourceType): Flow<WatchHistoryEntity?>`（純新增 query，**無 migration**），repository 暴露 Flow，`DetailViewModel` 改 collect。

**注意**：`:225-229` 的 `if (progress != null)` 要改成同時處理 null，否則刪記錄後不會歸零。換 id 時（`retargetTo:209`）要比照 `favoriteJob` 取消重訂。

**副作用**：Detail 在背景時仍持續訂閱（單列查詢，成本可忽略）。

> Navigation Compose **沒有官方「返回時觸發」回呼**。用 ON_RESUME 重查是次選（每次 resume 多查一次 DB，且可能與 `refresh()` 的 state 更新交錯）。

#### 10. 換線帶進度

**⚠️ 不要用 `duration - 15_000` 這個魔數**：短片（duration < 15 秒）會變負數；而且「已看完的片」（`PlayerScreen.kt:144` 在 STATE_ENDED 存 `position = duration`）會變成**每次點進去都從結尾前 15 秒開始**。

**正確修法**：
- 「已看 ≥95% 視為看完，resume 歸 0」
- resume 不在 `LaunchedEffect` 立即 seek，改在 `STATE_READY` 後以實際 `duration` clamp
- 換線期間不要存檔——**不用旗標**（旗標漏清會永遠不再存檔），改用不變式：迴圈內比對 `exoPlayer.currentMediaItem?.localConfiguration?.uri.toString() == uiState.streamUrl`，不一致就跳過這輪

#### 11. saveProgress 可能靜默丟失

NavHost 預設 fade `tween(700)`：BACK 鍵的存檔（t≈0）會成功，`onDispose` 的存檔（t≈700ms）發出後 `viewModelScope` 幾微秒後就取消，**Room 查詢回來時協程已取消，`upsert` 從未執行**。

**實際損失有限**（被 10 秒自動存檔壓住）：只有 (a) 觀看不足 10 秒就退出 → 該片完全不出現在「繼續觀看」(b) 續播位置最多落後 10 秒。**不要當成「進度完全不會存」來修。**

**修法**：`viewModelScope.launch` 內包 `withContext(NonCancellable)`（`Dispatchers.Main.immediate` 會 inline 執行，一定進得了 NonCancellable 區塊）。更正統是注入 `@ApplicationScope CoroutineScope`（`DoplyApp.kt:37` 已有私有 appScope 可參考）。

### 第三批：資料層（防未來，不是修現況）

#### 12. Room：改成 downgrade-only + 打開 exportSchema

**初版報告說「唯一會讓使用者永久失去資料的路徑」——講得太重。** 五條 migration（1→2…5→6）路徑連續無缺口，升級時 fallback 不會觸發；downgrade 又會先被 PackageManager 用 `INSTALL_FAILED_VERSION_DOWNGRADE` 擋掉。

但 **Codex 的反駁是對的**：fallback 並未限定只在降版，**未來漏加一條升版 migration 仍會默默清庫**。這才是真正的價值所在。

```kotlin
.fallbackToDestructiveMigrationOnDowngrade()   // Room 2.6.1 有此 API，無參數（已驗證）
```

同時 `GimyDatabase.kt:18` 改 `exportSchema = true`，並加：

```kotlin
ksp { arg("room.schemaLocation", "$projectDir/schemas") }
```

**注意**：`app/build.gradle.kts` 目前沒有這個設定，只開 `exportSchema` 會出編譯警告。第一次 build 會產生 `app/schemas/.../6.json`，`.gitignore` 沒有 schema 條目，**這個檔案應該進版控**（是未來 migration test 的基準）。限制：v1–v5 沒有 JSON，`MigrationTestHelper` 只能測 6→7 以後。

**行為變更**：改完之後，未來少寫 migration 的升級會**直接 crash 而非默默清庫**。這是 fail loud，是好事，但等於把責任押在有 migration test 上。

#### 13. movieffm 的 id 穩定化

**⚠️ 不要換成穩定雜湊。** 第二輪查證：`SavedEntryRecovery` 的唯一呼叫點是 `DetailViewModel.kt:180`，**在使用者手動開啟該筆且拋 404 時**才跑，沒有批次入口。而換雜湊後舊 id **仍然開得起來**（`MovieffmSource.fetchVodDetail:93-95` 查的是 `slugDao.getSlug(vodId)`，舊列原封不動，不會 404）。

所以後果不是「失配後被救回」，而是 **split-brain**：舊收藏／歷史照常運作於舊 id，但列表／搜尋頁會為同一個 slug 鑄出新 id → `isFavorite(新id)` 回 false → **收藏過的片顯示沒收藏**，同一部片可被重複收藏、進度分裂在兩個 id 上，**沒有任何機制會自癒**。

**正確修法（零破壞）**：真正的病灶是 `registerSlug` 的正向 map 只存在記憶體，process 重啟後 `idToSlug` 是空的，碰撞遞增迴圈從頭跑，同一個 slug 可能算出跟已持久化的**不同** id。而 `MovieffmSlugDao`（`Daos.kt:154-172`）**只有 `vodId→slug`，缺反向查詢**。

```kotlin
@Query("SELECT vodId FROM movieffm_slugs WHERE slug = :slug LIMIT 1")
suspend fun getVodId(slug: String): Long?
```

讓 `registerSlug` 先問 Room 再算雜湊 → 函數變確定性，**既有 id 一個都不動**。

**⚠️ 實作障礙（第二輪沒提到，我補查的）**：`registerSlug` 是 `private fun`（非 suspend），4 個呼叫點中 `parseRelatedVods:534` 與 `parseSeriesVods:562` **也是非 suspend**，改查 Room 就要一起改成 suspend。可行，但不是「零改動」。

### 第四批：體驗優化（低風險）

#### 14. 搜尋要能分辨「全站掛掉」與「真的沒有」

`searchAllSources` 算出 `anySourceAnswered` 卻**丟掉了**，`PaginatedResult` 沒有欄位承載這個訊號，所以 UI 無法分辨，兩者都顯示「找不到」。

**修法**：`PaginatedResult`（`Models.kt:143-148`）**加一個帶預設值的欄位**（如 `val allSourcesFailed: Boolean = false`）——全專案 19 處建構點全用位置參數，加預設值**零破壞**；改 sealed type 要動全部 19 處 + 3 個簽章，**不建議**。

需改：`VodRepositoryImpl.kt:263-274`、`SearchViewModel.kt:14-28/81/119`、`SearchScreen.kt:302-305`。
`SearchResultMergeTest` 不受影響（測的是 `mergeSearchResults` 的 List 行為）。首頁／分類頁不受影響（新欄位有預設值）。

#### 15. Hero 輪播聚焦時暫停

**已實證**：畫面停在「不是你的戀愛」(3/6)、焦點在「觀看詳情」，按 OK 進入的卻是「財閥X刑警第二季」。成因是 `HomeScreen.kt:241-245` 每 7 秒換一張，不管焦點在不在上面。

**修法**：`btnFocused` 目前宣告在 `:363`（在 `if (isTV)` 區塊內），要**上提到 `HeroBanner` 頂層**才能被 `:241` 的 `LaunchedEffect` 讀到，加進 key 並在聚焦時 early return。`:370` 的賦值與 `:391-392` 的 `◀ 觀看詳情 ▶` 文字都改讀上層變數。手機不受影響（手機按鈕 `:346-356` 不讀焦點狀態）。

**⚠️ 已知副作用**：TV 上焦點常自然停在這顆按鈕，只要焦點不離開 banner 就**永遠停在同一張**。使用者有出路（`:373-385` 的左右鍵可手動切換），但若不接受，改成「聚焦時延長 delay 而非 return」較安全。

#### 16. 集數格線改 lazy

`DetailScreen.kt:586-643` 是純 `for` 迴圈，整包塞在 LazyColumn 單一 `item{}` 內。**沒有任何集數上限**（parser 與 normalizer 都查過），長篇動畫 1000+ 集會整包展開。實務主力是幾十集，屬長尾風險。

**⚠️ 不要用 `LazyVerticalGrid`**：直接塞進 LazyColumn 的 item 會拋 `Vertically scrollable component was measured with an infinity maximum height constraints`；給固定高度則變巢狀捲動，TV 的 DPAD 下鍵會卡在內層捲不出去。

**正確修法**：改寫成 `LazyListScope.episodeGrid()` 擴充函式，`items(group.episodes.chunked(cols))` 每列各發一個 item，維持單一捲動容器。

**必踩點**：
- `CompositionLocal` 不能在 `LazyListScope` 讀，`:581-582` 的 `LocalIsTelevision.current` / `LocalDimensions.current` 要搬進 `item{}` 或由呼叫端傳入
- 間距要自己補：原本的 `Column(padding(horizontal = ...))`（`:583`）與 `Spacer(5.dp)`（`:642`）在每個 item 內都要重下
- 最後一列補齊已有處理（`:636-640`），照搬即可
- **焦點上下移動在拆 item 後無法靜態確認，需實機驗**
